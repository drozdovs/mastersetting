# Шлюз FX3 / FX3A: исследование путей и парной записи

Статус: **исследование выполнено на реальных образцах; парная запись НЕ проверена на камерах.**
Дата: 2026-11-23. Образцы: `/Users/sd/Desktop/Sony FX Drozdov/Settings/{FX3,FX3A}`.

## 1. Что исследовано (реальные данные)

### Образцы файлов настроек

| Файл | Размер | SHA-256 | Заголовок |
|---|---|---|---|
| `Settings/FX3/FX3.DAT` | 47 549 Б | `9b0527e6…3529` | `SONY0` + `ILME-FX3` |
| `Settings/FX3A/FX3A.DAT` | 47 549 Б | `1ee1d6b0…c44f` | `SONY0` + `ILME-FX3A` |

Наблюдения:
- Размер одинаковый, структура записей почти идентичная.
- Отличий по байтам: **805**; первое отличие — на смещении 13 (строка модели).
- Префикс `SONY0` (5 байт) — признак «файл настроек Sony» (используется в `load.sh`
  и `load.ps1` как `dat_note`).
- Внутри файлов **нет строк с путями** (ни `/`, ни `PRIVATE`, ни `SETTING`) —
  файл не указывает своё место на карте.
- В заголовке есть строка-дата, напр. `20261022_165003` (FX3) и `20261022_165044` (FX3A).

### Целевые пути на карте (источник истины)

Взято из рабочих скриптов пользователя `load.sh` / `load.ps1`, которые уже
проверены на практике:

```
<SD>/PRIVATE/SONY/SETTING/<КАМЕРА>/CAMSET/<КАМЕРА>.DAT
```

Отсюда:

```
FX3  -> PRIVATE/SONY/SETTING/FX3/CAMSET/FX3.DAT
FX3A -> PRIVATE/SONY/SETTING/FX3A/CAMSET/FX3A.DAT
```

## 2. Главный вывод по шлюзу

**Конфликта путей НЕТ.** Комплекты FX3 и FX3A лежат в **разных папках**
(`SETTING/FX3/...` против `SETTING/FX3A/...`), файлы имеют разные имена
(`FX3.DAT` против `FX3A.DAT`). Общая у них только родительская папка
`PRIVATE/SONY/SETTING/`, но её содержимое не пересекается.

Значит, с точки зрения файловой системы:
- один комплект **не перезапишет** другой;
- на одной карте физически могут одновременно лежать оба комплекта;
- сценарий «пара» технически возможен без обхода через «активную модель».

Это отличается от пессимистичного сценария, который закладывало ТЗ
(«если нативные пути двух комплектов конфликтуют…»). Обходной путь не нужен.

## 3. Что этим ещё НЕ доказано (важная оговорка)

ТЗ прямо предупреждает: «совместное присутствие файлов на карте ещё не означает
совместную доступность в меню камер». Поэтому остаётся непроверенным:

1. **Читает ли FX3 свою папку, игнорируя `SETTING/FX3A/`** — и наоборот. Ожидаемо да,
   но подтверждения с картой нет.
2. **Не «залипает» ли камера** при виде чужого комплекта в соседней папке.
3. **Ограничение числа наборов** на карте и совместимость по версии прошивки.
4. Правильно ли камера выбирает активный набор, если оба присутствуют.

До проверки на реальных FX3 и FX3A парная запись считается **непроверенной**.

## 4. Следствие для ядра: копировать только нужный файл

**Устаревший движок** (копировавший корень карты целиком, отсекая лишь медиа по
расширению) **удалён**. Именно он был дефектом, о котором говорит ТЗ. Теперь
работает `mastersetting/settings_rules.py`, который переносит только файлы
настроек.

Из исследования вытекает подтверждённое правило для FX3/FX3A:

```python
# Правило определения файлов настроек для семейства FX3/FX3A
CARD_SETTINGS_ROOT = "PRIVATE/SONY/SETTING"
# для модели M ожидаем ровно: PRIVATE/SONY/SETTING/<M>/CAMSET/<M>.DAT
```

То есть для этих камер нужно копировать **один конкретный файл**, а не дерево.
Это делает операции быстрыми, безопасными и не задевающими видеоматериал.

## 5. Статус согласования (обновлено 2026-11-24)

- **Пути подтверждены образцами.** Реальные файлы
  `/Users/sd/Desktop/Sony FX Drozdov/Settings/{FX3,FX3A}` распознаны по сигнатуре
  `SONY0`, а рабочие скрипты `load.sh`/`load.ps1` пишут ровно в
  `PRIVATE/SONY/SETTING/<МОДЕЛЬ>/CAMSET/<МОДЕЛЬ>.DAT`. Пути **совпадают** с ними.
- **Конфликта путей нет** (раздел 2). Тест
  `test_pair_write_with_real_samples_to_native_paths` пишет оба реальных образца
  на одну карту в разные папки и проверяет, что оба остались на месте.
- Состав набора — ровно **один** `.DAT` в `CAMSET` (по образцам и скриптам).
- **Не проверено на камерах:** читает ли FX3 свою папку, игнорируя `SETTING/FX3A/`,
  и не «залипает» ли камера. Это закрывается только тестом с FX3 и FX3A.

### Статус в коде (2026-11-24)

Правила FX3/FX3A в `mastersetting/settings_rules.py` по-прежнему помечены
**`confirmed=False`** — так шлюз не включается сам. Парная запись активируется
**явной командой** оператора, а не догадкой из скриптов:

```bash
python cli.py confirm-fx3-paths \
  --fx3-dir  "PRIVATE/SONY/SETTING/FX3/CAMSET" \
  --fx3a-dir "PRIVATE/SONY/SETTING/FX3A/CAMSET" --by "Иван"
```

Файла `fx3_paths_confirmed.json` на боевой машине пока нет, поэтому в UI пары
остаются выключенными до подтверждения. Это соответствует ТЗ: без образцов с
карты и без теста с двумя камерами парную запись не объявляем рабочей.

### Что уже готово для парной записи (в ядре, но выключено)

Чтобы после подтверждения путей не писать логику заново, конфликт уже
обнаруживается кодом:

- `library.find_path_conflicts(набор_FX3, набор_FX3A)` — возвращает совпадающие
  пути (сравнение без учёта регистра);
- `library.plan_pair_write(...)` — собирает общий план записи и **выбрасывает
  `PairWriteError` при конфликте**; для неполной пары отдаёт предупреждение и
  планирует имеющуюся часть;
- тесты `tests/test_acceptance.py`: `test_same_target_path_means_conflict`,
  `test_conflicting_pair_write_is_refused`,
  `test_compatible_pair_write_allowed`,
  `test_incomplete_pair_warns_but_allows_present_part`.

Осталось **только** заполнить реальные пути и включить `confirmed=True` — сама
защита от двойной записи уже проверена тестами.

### Как включить парную запись после съёмки путей

1. Сохранить настройки прямо с камеры: `Меню → Setup → Save/Load Settings → Save`.
2. Подключить карту, снять реальные пути и имена файлов.
3. Заполнить `settings_dirs` и поставить `confirmed=True` у нужного правила.
4. Добавить тест с реальным путём; только после этого разблокировать UI пар.

#### Как именно снять пути (готовая команда)

Сохранение настроек с камеры кладёт на карту **свой** набор файлов. Чтобы
увидеть их реальные пути и имена, есть команда `inspect`. Она показывает
**все** файлы карты и для каждого — причину, почему он принят или отклонён:

```bash
# macOS: карта обычно смонтирована в /Volumes/<ИМЯ>
python cli.py inspect --media "/Volumes/НОВАЯ КАРТА"

# Windows: буква карты, например E:\
python cli.py inspect --media "E:\\"
```

Пример вывода (на реальном образце FX3):

```json
{
  "settings_files": ["FX3.DAT"],
  "all_files": [
    {"rel_path": "FX3.DAT", "size": 47549, "accepted": true, "reason": "сигнатура SONY0"}
  ]
}
```

**Что прислать разработчику, чтобы включить правило:**

1. полный вывод `python cli.py inspect --media "<карта>"` в виде JSON;
2. отдельно, **для FX3 и для FX3A** (снимается один раз на каждую модель);
3. ответы на вопросы ниже.

#### Вопросы, которые нужно закрыть (по ТЗ)

1. **Точные пути.** Нашлась ли папка вида `PRIVATE/SONY/SETTING/<МОДЕЛЬ>/CAMSET/`?
   Или путь другой (например, без `<МОДЕЛЬ>` или без `CAMSET`)?
2. **Состав набора.** Комплект — это всегда **один** `.DAT`, или в `CAMSET`
   бывает несколько файлов?
3. **Проверка на камерах.** Можете ли проверить на реальных FX3 и FX3A, что оба
   комплекта на одной карте не мешают друг другу?
4. **Слот.** `load.sh` пишет «если слота два, карту ставьте в слот 1» — это
   требование к нам или просто подсказка?

#### Что произойдёт после ответов

Ничего не нужно переписывать: защита от конфликта уже готова и протестирована
(`library.plan_pair_write` + `find_path_conflicts`). Останется одной командой
подтвердить пути — и парная запись включится сама:

```bash
# Пути снимаются из образца и сразу применяются + проверяются на конфликт
python cli.py confirm-fx3-paths --from-sample "/Volumes/НОВАЯ КАРТА" --by "Иван"

# Либо явно, если пути уже известны:
python cli.py confirm-fx3-paths \
  --fx3-dir  "PRIVATE/SONY/SETTING/FX3/CAMSET" \
  --fx3a-dir "PRIVATE/SONY/SETTING/FX3A/CAMSET"
```

Команда пишет подтверждение в `app_data_dir/fx3_paths_confirmed.json`
(переопределяется `MS_FX3_CONFIRM_FILE`), помечает правила `confirmed=True`
и сообщает `pair_write_available`. После этого при следующем старте UI сам
разблокирует выбор пары в мастере записи (`AppController.__init__` вызывает
`path_confirm.apply_to_rules()`). Если пути позже окажутся неверными — удалите
этот файл, и шлюз снова закроется.

Примеры, которые нужно различать при снятии путей с карты:

```
PRIVATE/SONY/SETTING/FX3/CAMSET/FX3.DAT   (текущая гипотеза из скриптов)
PRIVATE/SONY/SETTING/CAMSET/FX3.DAT
PRIVATE/SONY/PRO/SETTING/FX3.DAT
```

### Когда пути будут получены

1. Подтвердить пути командой `confirm-fx3-paths` (см. выше).
2. Проверить на реальных FX3 и FX3A, что оба комплекта на одной карте не мешают
   друг другу (раздел 3).
3. Только после этого считать парную запись проверенной и объявлять её в README.
